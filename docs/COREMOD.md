# The coremod

Albedo needs to run code at points in vanilla rendering that Forge does not
expose as events. It gets there by rewriting bytecode at class-load time.

This is the pre-1.13 mechanism — `IFMLLoadingPlugin` plus an
`IClassTransformer`, not the JSON/JavaScript coremods of later versions.

| Class | Role |
| --- | --- |
| `asm/FMLPlugin` | The `IFMLLoadingPlugin` entry point. Names `ASMTransformer` as the transformer and `AlbedoCore` as the container. Excludes `elucent.albedo.asm` from transformation so it cannot patch itself. |
| `asm/AlbedoCore` | A `DummyModContainer` so FML lists the coremod as a mod (`albedocore`). Does nothing else. |
| `asm/ASMTransformer` | All the actual patching. |

The manifest entries that make FML load this (`FMLCorePlugin`,
`FMLCorePluginContainsFMLMod`) are generated by the build from
`coreModClass` in `buildscript.properties` — do not hand-write them.

## What gets patched

Six targets. Each injects one static call; none changes control flow.

| Target class | Method (deobf / SRG) | Injected call | Why |
| --- | --- | --- | --- |
| `renderer.ChunkRenderContainer` | `preRenderChunk` / `func_178003_a` | `RenderUtil.renderChunkUniforms(RenderChunk)` | Tells the terrain shader which chunk it is about to draw, so it can place vertices in world space. |
| `renderer.entity.RenderManager` | `renderEntity` / `func_188391_a` | `RenderEntityEvent.postNewEvent(Entity)` | Per-entity hook: lets Albedo set that entity's position before it draws. |
| `renderer.tileentity.TileEntityRendererDispatcher` | `render` / `func_180546_a` | `RenderTileEntityEvent.postNewEvent(TileEntity)` | Same, for block entities. |
| `renderer.GlStateManager` | `enableLighting` / `func_179145_e` and `disableLighting` / `func_179140_f` | `RenderUtil.enableLightingUniforms()` / `disableLightingUniforms()` | Vanilla toggling fixed-function lighting is Albedo's cue to match. |
| `profiler.Profiler` | `endStartSection` / `func_76318_c` | `ProfilerStartEvent.postNewEvent(String)` | **The important one.** Vanilla's profiler section names are how Albedo knows which pass of the frame is starting. See [RENDER_PIPELINE.md](RENDER_PIPELINE.md). |
| `client.ForgeHooksClient` | `handleCameraTransforms` | `RenderUtil.setTransform(TransformType)` | Records the item transform being used. **Currently vestigial** — nothing reads the field it sets. |

Using the profiler as a render-phase signal is unusual, and worth understanding
before changing anything: Albedo is not profiling, it is using the section names
vanilla already emits as a free, ordered description of the frame.

## How a patch is written

Every patch method follows the same shape:

```java
ClassNode classNode = new ClassNode();
new ClassReader(bytes).accept(classNode, 0);
for (MethodNode m : classNode.methods) {
    if (!m.name.equals(targetMethod) || !m.desc.equals(targetDesc)) continue;
    // insert a MethodInsnNode (+ the VarInsnNode that loads its argument)
}
ClassWriter writer = new ClassWriter(3);
classNode.accept(writer);
return writer.toByteArray();
```

Points to be careful about:

- **Obfuscated and deobfuscated names both matter.** Each patch takes an
  `obfuscated` flag and picks SRG names (`func_178003_a`) or MCP names
  (`preRenderChunk`) accordingly. The flag is derived in `transform` by
  comparing `name` against `transformedName`. Getting this wrong means the patch
  silently does nothing in one environment and works in the other — always test
  a **built jar**, not just the dev client.
- **Match on descriptor as well as name.** Several targets are overloaded.
- **`InsnList` is not `Iterable`** in this ASM version despite having
  `iterator()`. Iterate `code.toArray()`.
- **Injection order reads backwards.** Where a call needs an argument, the
  `MethodInsnNode` is inserted first and the `VarInsnNode` that loads the
  argument is inserted at the same index afterwards, which places the load
  *before* the call. Inserting them in the "natural" order produces bytecode
  that fails verification.

## Verifying the patches applied

Each successful patch prints to stdout at load. In `run/logs/latest.log`:

```
Successfully loaded Profiler ASM!
Successfully patched ForgeHooksClient!
Successfully loaded GlStateManager ASM!     (twice - enable and disable)
Successfully loaded RenderManager ASM!
Successfully loaded RenderChunk ASM!
Successfully loaded TileEntityRendererDispatcher ASM!
```

If any line is missing, that hook did not apply and the feature depending on it
is silently dead. This is the first thing to check when "Albedo does nothing".

## Interaction with other coremods

OptiFine and shader mods rewrite several of these same classes. Albedo matches
methods by exact name and descriptor, so another transformer that changes a
signature will make Albedo's patch quietly miss. Note also that Albedo cannot
even be loaded alongside OptiFine in a ForgeGradle dev workspace — OptiFine
ships against obfuscated Minecraft and fails before Albedo is reached — so that
combination must be tested in a packaged client.
